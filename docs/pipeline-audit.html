System Design & Architecture

MAARA System Design

Full architectural map of MAARA AI Business Manager — a multi-tenant daily sales & expense reporting platform for hospitality operators. Written from a complete read of backend/ and frontend/src/ (~6,000 LOC), reflecting the repo after the MODEL 2 + range-filter change.

Frontend React 19 · Vite 8 · TypeScript 6 Backend FastAPI · SQLAlchemy 2 · Pydantic 2 · Py 3.12 Data Supabase Postgres 15+ · Alembic Auth Supabase Auth · JWT ES256 / JWKS Deploy Vercel · Render · Supavisor pooler
01

Overview & stack

One product, one live tenant today (Dosa n Chutney), built multi-tenant from the schema up. A staff member fills a Daily Sales Report once (or several times) a day; managers read Sales, Expenses and Profit dashboards that aggregate every saved entry.

The defining architectural decision: a report's shape is data, not code. Templates, sections, fields and calculation formulas all live in the database as versioned rows. The backend has a small safe interpreter (calculations/) that executes those formulas. Adding a new report type — or a new business with a completely different daily sheet — is a data operation, not a deploy.

Frontend

  • React 19 + Vite, TypeScript, no router (one App state gate)
  • @supabase/supabase-js holds the session; token attached per request
  • Charts hand-built in SVG/CSS — zero charting deps
  • State: useState + useEffect + fetch. No Redux/Zustand/React-Query

Backend

  • FastAPI, 4 routers, dependency-injected auth + DB session
  • Layered: api → services → repositories → models
  • SQLAlchemy 2 ORM, psycopg (v3) driver, Alembic migrations
  • Calculation engine is a standalone pure library (no DB, no eval)

03

Architecture

Five tiers. The client never reaches the database; the API never trusts an organization_id from a request body; the browser holds the only long-lived credential.

Client React SPA served as static files. supabase-js owns the session (access + refresh token in localStorage). Every backend call goes through apiFetch, which injects Authorization: Bearer <access_token>.
Identity Supabase Auth issues an ES256 JWT on sign-in. The backend never calls Supabase to check it — it verifies the signature against Supabase's public JWKS document (fetched once, cached ~1h) and trusts only the sub claim.
API FastAPI on Render. Routers: auth, daily-reports, dashboards, report-templates. Two DI dependencies run on almost every route: get_current_user (identity) and require_role(...) (org membership + rank).
Domain Services hold the business logic and own the transaction; repositories are the only place SQL is written and the layer where "filter by organization_id" becomes a real WHERE. The calculation engine is a leaf library the save path calls.
Data Postgres on Supabase, reached through the Supavisor session pooler (IPv4). 13 tables. Schema owned entirely by Alembic; a Postgres trigger keeps profiles in sync with auth.users.

Backend layering rule

A router function does three things only: declare its dependencies (auth, DB, role), call one service function, return. It contains no SQL and no business logic. Services never import fastapi except to raise HTTPException. Repositories never import services. This keeps the calculation engine and the aggregation logic unit-testable without a running app.

04

Write path — save a Daily Report

The critical path. A staff member types the day's takings and hits Save Daily Report.

  1. Keystroke → updateSales / updateExpense / updateSummary run isAcceptableNumberInput: only digits, one dot, optional leading minus, magnitude < MAX_MONEY (1011). A bad character is rejected, never stripped. totalSales / totalExpenses recompute via useMemo as a preview. DailyReportPage.tsx · lib/validation.ts

  2. On mount, effect A calls fetchMe() and picks the dosa-n-chutney org (or the first membership) → organizationId. Effect B (on org/date change) calls fetchDailyReport purely to know if an entry already exists for that date — it never populates the form. The form always starts blank. DailyReportPage.tsx effect A / B

  3. Save → handleSave builds { values: {field_key: string}, expenses: [{description, amount}] } and calls saveDailyReport → PUT /organizations/{id}/daily-reports/by-date/{date}. reportsApi.ts

  4. apiFetch reads session.access_token from supabase-js, sets the bearer header, JSON.stringifys the body. Non-2xx → throw new ApiError(detail, status). api/client.ts

  5. FastAPI resolves get_current_user: _JWKSVerifier.verify pulls Supabase's signing key via PyJWKClient (cached), then jwt.decode(token, key, algorithms=["ES256","RS256"], audience=settings.supabase_jwt_audience, require=["exp","sub"], leeway=30). The sub becomes AuthenticatedUser.id. Any PyJWTError → 401 "Invalid or expired session. Please sign in again." auth/dependencies.py

  6. require_role("staff") → get_membership: organization_id comes from the URL path; a SELECT on organization_members confirms the caller has a row for it. Missing → 403 (identical error whether the org is absent or just not yours). auth/permissions.py

  7. report_service.save_daily_report: resolve the org's daily-operations template and its published version (org-scoped query). Reject any values key that isn't a non-calculated field on that version → 422. services/report_service.py · repositories/template_repository.py

  8. create_report always INSERTs a new daily_reports row (MODEL 2). It pins template_version_id now and never repoints it. repositories/daily_report_repository.py

  9. Coerce each raw value with _to_decimal (blank / invalid → Decimal("0")). Reject any field or expense amount ≥ MAX_AMOUNT (1012, the NUMERIC(14,2) ceiling) with a clean 422. Sum expense rows → total_expenses. report_service.py

  10. Calculation engine. validate_rules(fields, rules) parses each rule's operands against its Pydantic schema and topologically orders them; evaluate(...) executes apply_operation per rule over Decimals, feeding results back into the pool. This template: total_sales = SUM(card,cash,uber_eats,just_eat,deliveroo,other_sales), operating_profit = total_sales − total_expenses. A CalculationError → 422. calculations/evaluator.py · registry.py · graph.py

  11. One transaction: replace_expenses (delete none — fresh row — then insert), upsert_values (one row per field, NUMERIC(18,4)), report.status = "submitted", db.commit(). A stray DataError is caught, rolled back, and returned as 422 instead of a 500. daily_report_repository.py · report_service.py

  12. Response DailyReportOut (every stored value as a string). The form marks the entry “linked”, clears the “an entry already exists” banner, shows a confirmation. schemas/daily_report.py · DailyReportPage.tsx

MODEL 2

Every Save is an independent daily_reports row. Migration c1a2b3d4e5f6 dropped UNIQUE(report_template_id, report_date). Saving twice for one date → two rows → the dashboards sum them. There is no in-place edit; correcting a typo means the wrong number stays in the total unless you delete the row in SQL.

05

Read path — dashboards

All three dashboards are computed on read — no materialised aggregates, no cache. At current data volume (a handful of rows per day) plain SQL grouping is instant.

Sales Dashboard

  1. Component holds range state (7 | 30 | 90 | all, default 30). On change it fetches sales/daily?days=N where N = fetchWindowDays(range) — double the window for fixed ranges (so it can also show the preceding period), 36500 for all-time. SalesDashboard.tsx · lib/dashboardRange.ts

  2. dashboard_service.sales_daily loads every daily_report with report_date ≥ today − days, eager-loading values + fields, then groups by date: multiple reports on one date are summed into a single daily row (the MODEL 2 fix). services/dashboard_service.py

  3. Client splits the returned rows into current vs previous period via splitByRange, then derives everything: total, per-channel breakdown, daily trend (last 30 bars), delivery-platform split, growth vs previous period, latest-day figure. SalesDashboard.tsx

Expenses Dashboard

Three parallel fetches: expenses/daily?days=N (new endpoint, group-by-date total), expenses/by-category?since&until (range from the same filter), expenses/recent?limit=15. KPIs, trend, category donut and the recent table all follow the range toggle.

Profit Track

Two fetches: profit/monthly?months=7 (revenue / expenses / profit per month) and profit/daily-summary?date= for the currently-selected report date. daily_summary sums every entry for that date, computes expected_cash = opening + cash_sales − expenses vs the counted cash_balance, and a variance. |variance| < 1 reads as “reconciled”.

Read-path caveat under MODEL 2

opening_cash, cash_balance and next_day_open_cash are snapshots, not flows — summing them across a day's multiple entries (which daily_summary now does) is wrong. If more than one Save per day becomes routine, the cash reconciliation needs to take the latest entry's snapshot fields and sum only the additive ones.

06

The template engine

A report type is four nested row-sets, all versioned:

report_templates            stable identity — "Daily Operations Ledger", key "daily-operations"
  └─ report_template_versions   draft → published → archived; version_number
       ├─ report_sections       "Income / Sales", "Expenses", "Summary" (display_order)
       │    └─ report_fields    opening_cash, card_sales… — field_type, is_calculated, JSONB metadata
       └─ calculation_rules     {operation, operands(JSONB)} — key matches a calculated field

Why versions are frozen

When a daily_reports row is created it pins template_version_id and never repoints it. A report filed in March always renders and recalculates against the template as it was in March, even after the template is edited. Editing a template = drafting a new version (template_service.create_draft_version), which publish_version promotes only after validate_rules passes — report_templates.current_version_id then swings to it (a deferred FK, post_update=True, breaks the circular reference).

Extensibility hatches

  • report_fields.field_metadata (DB column metadata, JSONB) — select options and other per-field config without a schema change.
  • expense_categories is rows, not an enum: organization_id IS NULL = a system default visible to every org (partial unique index on key); set = that org's custom addition.

The template CRUD API (report_templates.py, 6 routes, admin-gated) is complete and tested via the engine, but has no admin UI — today templates change by API call or SQL only.

07

The calculation engine

A self-contained library over Decimal — no database, no eval, no exec. A rule is {operation, operands}; operands is validated against a closed Pydantic schema chosen by operation. An operand is either a ref (another field/rule key) or a literal const — the model rejects setting both.

Operations (9, closed set)

OpOperandsNotes
SUMitems[]refs and/or consts
SUM_GROUPgroupsums every field in a section; membership resolved by the evaluator, not a ref
SUBTRACT MULTIPLY DIVIDEleft, rightDIVIDE by 0 → typed error at evaluate time
PERCENTAGEnumerator, denominator× 100; 0 denominator → typed error
MIN MAXitems[]—
ROUNDvalue, decimals (0–6)ROUND_HALF_UP, not banker's rounding

Two entry points

  1. validate_rules(fields, rules) — run once, at publish. Parses every operand; checks every ref resolves to a known field or rule and every SUM_GROUP names a real section; runs graph.topological_order (DFS) to detect cycles and produce a safe evaluation order. A version that fails cannot be published. calculations/evaluator.py, graph.py

  2. evaluate(fields, ordered_rules, raw_values) — run on every save. Takes the pre-proven order and just executes each rule. The hot path never re-derives the graph. Caller contract: every non-calculated field must be present in raw_values (default blanks to 0) — a gap raises a typed MissingDependencyError, never a bare KeyError. calculations/evaluator.py, registry.py

Cycle-detection subtlety (tested)

A subtotal like total_sales lives in the sales section it sums — that is not a self-cycle and is explicitly excluded. But two rules that SUM_GROUP each other's home section is a real cycle and is caught. Both cases have dedicated tests.

The auth.users → profiles trigger

Created in migration 1: a SECURITY DEFINER plpgsql function on AFTER INSERT ON auth.users inserts a matching profiles row (ON CONFLICT DO NOTHING). So a profile exists the instant someone signs up — no just-in-time creation, no race. GET /me still self-heals a missing profile defensively (Profile(id=sub, display_name=email)).

09

Auth & multi-tenancy

Two independent checks on every protected route.

Who are you

_JWKSVerifier.verify: PyJWKClient(jwks_url, cache_keys=True, lifespan=3600) fetches the signing key, then jwt.decode with ["ES256","RS256"], audience from config (authenticated), require=["exp","sub"], 30s leeway. Only sub → AuthenticatedUser.id is trusted.

Can you touch this org

get_membership(org_id_from_path, db, user) → one SELECT on organization_members. require_role("manager") wraps it and compares ROLE_RANK = {staff:0, manager:1, admin:2, owner:3}. Daily reports + dashboards need staff; template writes need admin.

Invariant

The organization_id in every URL is checked against a real membership row. It is never read from a request body. A missing membership and a non-existent org return the same 403 — the API doesn't leak which orgs exist. Every repository function takes organization_id and filters by it in SQL.

Row-Level Security is not enabled on the Postgres tables. Tenant isolation is 100% application-layer. A single missing WHERE organization_id = ... would be a cross-tenant leak. RLS is the intended defence-in-depth follow-up.

Test coverage

20 tests, all in tests/unit/test_calculations.py. They cover the calculation engine thoroughly: an end-to-end Dosa-shaped template (SUM_GROUP → SUBTRACT → PERCENTAGE → nested ROUND, Decimal-exact), every operation individually, float-drift avoidance (0.1+0.2+0.3 == 0.6), and every failure mode (unsupported op, malformed operands, ref+const, missing ref, missing section, direct / self / cross-rule cycles, divide-by-zero, missing raw value).

Coverage gaps

Nothing tests: the API layer, auth / JWKS verification, report_service orchestration (including the MODEL 2 insert and the MAX_AMOUNT guard), dashboard_service aggregation (the group-by-date logic), repositories, or any frontend code. No integration test spins up the app + a test database.
